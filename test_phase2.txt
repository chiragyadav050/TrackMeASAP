BLOCKED — WHAT IS MISSING AND HOW TO FIX IT
===============================================================================

BLOCKED ITEM : Browser-level E2E (48 tests). Unchanged from Phase 1.

WHAT IS MISSING
  Real Clerk API keys. The committed .env holds syntactically valid
  placeholders that no Clerk instance stands behind.

WHY
  A Clerk development key makes the middleware perform a handshake: with no
  __clerk_db_jwt cookie the browser is redirected to the instance's Frontend
  API host. That host does not exist, so Clerk answers
  {"errors":[{"message":"Invalid host","code":"host_invalid"}]} and the
  browser never reaches the app. Server-side requests are unaffected, which
  is why the 5 API tests pass against the real server and database.

HOW TO FIX
  1. Create an application at https://dashboard.clerk.com
  2. Copy both API keys into .env
  3. pnpm test:e2e     — all 53 run, no code change needed
  tests/e2e/clerk-env.ts detects a real instance by decoding the publishable
  key and un-skips automatically.

WHAT WAS NOT DONE, AND WHY
  Clerk was NOT mocked. A task test that stubs authentication proves only
  that the stub works. The rules that actually matter here — cross-tenant
  ownership on every read and write — are instead covered FOR REAL by 20
  integration assertions against a live database with two real profiles.
