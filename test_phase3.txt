HAND-WRITTEN SQL appended to the migration:

  CREATE UNIQUE INDEX "semesters_one_current_per_profile"
    ON "semesters" ("profile_id") WHERE "is_current";

  A PARTIAL unique index, which Prisma's schema language cannot express. A
  plain UNIQUE(profile_id, is_current) would also forbid a second NON-current
  semester, which is exactly backwards.

VERIFIED IN THE LIVE DATABASE (psql pg_indexes):
  CREATE UNIQUE INDEX semesters_one_current_per_profile
    ON public.semesters USING btree (profile_id) WHERE is_current

  …and verified BEHAVIOURALLY by an integration test that bypasses the
  service entirely and asserts the database itself rejects a second current
  semester.

BLOCKED — WHAT IS MISSING AND HOW TO FIX IT
===============================================================================

BLOCKED ITEM : Browser-level E2E (62 tests). Unchanged since Phase 1.

WHAT IS MISSING
  Real Clerk API keys. The committed .env holds syntactically valid
  placeholders that no Clerk instance stands behind.

WHY
  A Clerk development key makes the middleware perform a handshake: with no
  __clerk_db_jwt cookie the browser is redirected to the instance's Frontend
  API host. That host does not exist, so Clerk answers
  {"errors":[{"message":"Invalid host","code":"host_invalid"}]} and the
  browser never reaches the app. Server-side requests are unaffected, which is
  why the 5 API tests pass against the real server and database.

HOW TO FIX
  1. Create an application at https://dashboard.clerk.com
  2. Copy both API keys into .env
  3. pnpm test:e2e     — all 67 run, no code change needed
  tests/e2e/clerk-env.ts detects a real instance by decoding the publishable
  key and un-skips automatically.

WHAT WAS NOT DONE, AND WHY
  Clerk was NOT mocked. The rules that actually matter here — attendance
  arithmetic, the one-current-semester constraint, cross-tenant isolation,
  the assignment/task boundary — are covered FOR REAL by 103 unit tests and
  104 integration tests against a live database.
