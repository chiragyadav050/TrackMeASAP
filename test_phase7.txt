3. THE SECURITY MODEL, AND THE TESTS THAT ATTACK IT
---------------------------------------------------

A linking token is the only thing between a stranger's Telegram account and a
user's entire life — tasks, grades, finances, health. The tests attack the
flow rather than merely exercising it.

3.1 The plaintext token is NEVER stored
  Only a SHA-256 hash reaches the database. Asserted directly: the stored row
  does not equal the token, equals its hash, and `JSON.stringify(row)` does
  not contain the token anywhere. A database dump contains no usable tokens.

3.2 128 bits of entropy
  16 random bytes as hex. Asserted by format. Brute force is not "expensive",
  it is irrelevant.

3.3 Single use
  Redeeming a token marks it consumed INSIDE the same transaction, and only
  `WHERE consumedAt IS NULL`, so two simultaneous redemptions cannot both
  succeed. Replay from a second chat is refused. Tested.

3.4 Expiry — 10 minutes
  Tested at both edges: refused one minute after expiry, accepted one second
  before it.

3.5 Generating a new code kills the old one
  A user who clicks "generate" twice holds exactly ONE live secret, not two.
  Tested: the first token becomes invalid the moment the second is issued.

3.6 Constant-time comparison
  Hashes are compared with `timingSafeEqual`. `===` on hex short-circuits at
  the first differing character, leaking how much of a guess was correct.

3.7 A chat cannot be silently re-pointed
  If chat X is linked to profile A, profile B's valid token CANNOT claim it —
  whoever controls that chat would otherwise inherit B's data. Tested, and the
  original owner is verified still in place afterwards.

3.8 The bot is not an oracle
  "Invalid", "expired" and "already used" produce the SAME reply. Asserted by
  comparing the two replies for equality — telling a stranger which of the
  three it was turns the bot into a probe for token validity.

3.9 Unlinking really revokes
  The chat can no longer reach the profile, and every pending token is
  destroyed, so an old code cannot re-establish access the user just revoked.
  The row survives with `isActive: false` for history.


4. THE WEBHOOK BOUNDARY
-----------------------

The endpoint is unauthenticated by necessity — Telegram calls it — so
everything protecting it lives in the route, and four E2E tests run
unconditionally against the real built server:

  - No secret header → 401 with an EMPTY body. Verified.
  - Wrong secret header → 401. Verified.
  - GET → 405. Answering GET would make it discoverable by a crawler.
  - No Telegram secret appears in the client bundle, checked both by name and
    by the shape of a bot token (`\d{8,}:[A-Za-z0-9_-]{30,}`).

  FAIL CLOSED: with no `TELEGRAM_WEBHOOK_SECRET` configured, every request is
  refused. An unconfigured secret must never mean "accept everything" — and
  the server log line proving this fired during the test run.

  The secret is checked BEFORE the body is read, so an unauthenticated caller
  cannot make the server parse arbitrary JSON.

  Once the secret checks out the route ALWAYS returns 200, even on a handler
  crash. Telegram retries anything else, and a retry storm on a bug is worse
  than a dropped message; the failure is logged instead.

  Per-chat rate limiting (30/min) and bot-to-bot messages rejected.


5. THE AI/BOT BOUNDARY RULE
---------------------------

The bot NEVER touches Prisma to mutate anything. Every write goes through the
same application service the web UI calls:

  /task   → createTask()          /check  → toggleHabitToday()
  /done   → setTaskCompletion()   /remind → createReminder()

Proven, not asserted: the `/task` test checks that the created task has the
SERVICE's defaults and that an ActivityEvent was written — which a raw insert
from the bot would not produce.

Identity comes ONLY from `telegramChatId`. Tested directly: a message reading
`/task profileId=<other user's id> steal` creates a task on the SENDER's
profile with that text taken literally, and creates nothing on the named
profile.

Cross-user isolation tested: a linked chat asking `/today` sees its own tasks
and never the other profile's, with both profiles' data present in the same
tables.


6. HONESTY IN THE BOT ITSELF
----------------------------

  - Plain text gets an honest refusal naming Phase 8, NOT an invented AI
    reply. Asserted.
  - `/remind` accepts one explicit `HH:MM what` form and REFUSES anything
    else rather than guessing. A wrong guess means a reminder that never
    fires, or fires at 3am. Asserted for "sometime tomorrow call mum".
  - `/done` and `/check` refuse an index with no prior listing, and refuse 0,
    99, "abc" and empty — verifying afterwards that nothing was completed.
  - `/task` with no title asks rather than creating an empty task.

  MarkdownV2 escaping is tested as a SECURITY property, not just a formatting
  one: a task title is user input, and the tests assert that
  `[click me](https://evil.example)` cannot inject a link into the bot's own
  output.


7. DEFECTS FOUND AND FIXED DURING THIS PHASE
--------------------------------------------

  1. **Blank optional env vars broke boot.** `TELEGRAM_BOT_TOKEN=""` — the
     natural way a `.env` says "not configured", and what `.env.example`
     ships — failed the format check, because `.optional()` does not skip an
     empty string. The whole app refused to start. Fixed with an
     `optionalSecret()` helper that normalises blank to undefined BEFORE
     validation, while still holding a value that IS present to its full
     format. Found by the integration suite failing to boot.

  2. **Per-chat command memory survived a change of owner.** The ordered task
     list behind `/done 2` was keyed by chat id alone. A chat unlinked by user
     A and then linked by user B inherited A's list, so B's `/done 1`
     referenced a task they cannot see. NO DATA LEAKED — the ownership check
     in `setTaskCompletion` refused it — but the user got "something went
     wrong" instead of "send /tasks first". Fixed by keying on chat AND
     profile. Found by a test, not by reading the code.

  3. **A leaked timer in the Telegram client.** The `AbortController` timeout
     was never cleared, so every send kept the event loop alive for ten
     seconds — meaning a worker shutdown would hang. Fixed with a `finally`.
     Surfaced as a lint error about an unused variable; the real defect was
     larger than the lint.

  4. **A pre-existing time-dependent test.** `setTaskCompletion` stamped
     `completedAt` from the wall clock while the test fixed the view's clock,
     so "completed today" broke once real time crossed local midnight in the
     test's zone — which happened DURING this session. Fixed properly by
     giving the service an injectable `now`, matching the convention every
     other service and derive module already follows, rather than loosening
     the assertion.
