3. THE DECISIONS THE TESTS DEFEND
---------------------------------

3.1 Quiet hours that WRAP MIDNIGHT
  22:00–07:00 is the normal case for sleep, and the naive test
  `minute >= start && minute <= end` is false for EVERY minute of it. That bug
  delivers notifications at 3am. The wrap is handled explicitly and tested
  from both sides, at both boundaries, and for the degenerate zero-length
  window (which silences nothing, so one mis-set field cannot mute the app
  permanently).

3.2 Held, never dropped
  A notification blocked by quiet hours or the daily limit stays PENDING and
  is re-evaluated by the flush job. A silenced reminder that never arrives is
  worse than a late one. Verified end to end: fired at 03:00 → PENDING; flushed
  at 09:00 → SENT.

3.3 Urgent bypasses everything
  An exam starting in ten minutes is exactly what notifications exist for, so
  urgent alerts ignore both quiet hours and the daily limit.

3.4 Recurrence is CALENDAR arithmetic
  "Monthly" means the same date next month, not +30 days; "yearly" survives a
  leap year; the clock time is preserved. WEEKDAYS walks forward at most seven
  days and returns null if no day is selected, rather than looping forever.

3.5 A deadline is a MOMENT, not a block
  Assignment and task due dates appear on the calendar with `isBusy: false`.
  Marking them busy would make every due date conflict with the time you
  booked to do it in — exactly backwards. Tested: a day with a deadline and no
  meetings reads as eight hours free.

3.6 Back-to-back is not a conflict
  Half-open intervals. A 10:00 finish and a 10:00 start do not overlap.
  Flagging consecutive meetings would make the warning noise users ignore.

3.7 Free-time gaps merge overlapping blocks first
  Two overlapping meetings are ONE busy period; treating them separately would
  invent a negative-length gap. Slots under the minimum are dropped — a
  seven-minute gap is not usable time.

3.8 One timeline, no duplication
  Classes, assignments, exams, tasks and personal events are PROJECTED into a
  single entry shape at read time. Nothing is copied into `calendar_events`,
  so editing a class in Academics cannot leave a stale calendar copy. Only the
  user's own events are editable on the calendar.

5. SECURITY / OWNERSHIP
-----------------------

tests/integration/schedule-authorization.test.ts — 14 tests. Reminders are the
highest-stakes surface in the app for isolation: a leak here does not merely
show someone else's data on a screen, it PUSHES it to a device.

  - Reminder and event guards return NOT_FOUND, never FORBIDDEN.
  - Reads: reminders, notifications, unread count and the calendar are all
    empty for another user.
  - Another user's events do NOT consume your free time and cannot create
    conflicts on your calendar. Two users booked at the same hour is not a
    conflict for either.
  - Notification settings are per profile: one user enabling quiet hours does
    not silence anyone else.
  - `markAllRead` with an explicit id belonging to another user marks nothing
    and returns 0.
  - Grafting refused: a reminder cannot be attached to another user's task,
    event or habit, and their OWN reminder cannot be re-pointed at one.
  - THE WORKER RESPECTS OWNERSHIP. A sweep over two profiles' reminders
    delivers exactly one notification to each, with no crossover.
  - The same `dedupeKey` for two different profiles is NOT a collision — the
    unique index is (profileId, dedupeKey), so two users can legitimately hold
    the same logical alert.
  - Worker logs deliberately exclude reminder titles and messages. A worker
    log is not the place for the contents of someone's private reminders.
  - Unauthenticated GET of /calendar returns non-200 with no user data.


6. RELIABILITY
--------------

  - Retries are exponential (2s base, 3 attempts) rather than fixed: a Redis
    blip recovers in milliseconds, but an upstream outage should not be
    hammered every second.
  - Notification delivery stops after MAX_ATTEMPTS (5) and is marked FAILED —
    an endlessly retrying send would fill the queue and hide real failures.
    Tested.
  - The sweep isolates failures PER REMINDER: one profile with bad data cannot
    stop every other user's reminders from firing.
  - `findDueReminders` is bounded (default 100) so one sweep cannot pull an
    unbounded backlog into memory after an outage.
  - REDIS IS OPTIONAL. `src/server/queue.ts` never connects at import time, and
    `enqueue()` returns `{queued: false}` rather than throwing when Redis is
    absent. The whole app is usable without a worker; only scheduled firing
    stops. `pnpm worker:once` runs the same sweep without Redis at all.
  - Queues are created lazily behind the same pattern as the Prisma client, so
    `next build` succeeds on a machine with no Redis.


7. DEFECTS FOUND AND FIXED DURING THIS PHASE
--------------------------------------------

  1. **BullMQ rejects `:` in queue names.** Names were `life-os:reminders`;
     the worker crashed at startup with "Queue name cannot contain :". Fixed
     by using BullMQ's supported `prefix` option instead, which is the correct
     way to namespace several apps in one Redis. Found by RUNNING the worker,
     not by reading the code.

  2. **`server-only` threw in the worker process.** Its published entry point
     throws outside the Next.js bundler — including in a process that is about
     as server-side as code gets. Fixed with a documented stub aliased through
     `tsconfig.worker.json`, so the real guard still protects the application
     build while the worker imports the same services the web app uses rather
     than a parallel copy that could drift.

  3. **Exam projection assumed an `endAt` column.** Exams store `startAt` plus
     `durationMinutes`. Caught by typecheck; fixed to compute the end, and to
     skip exams with no scheduled time rather than placing them at the epoch.

  4. A Phase 1 test asserted the health endpoint's exact response shape. Adding
     worker status is an intended Phase 6 change, so the assertion was widened
     — and strengthened, by additionally asserting the response contains no
     Redis URL or port.
